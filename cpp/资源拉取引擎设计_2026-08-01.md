# 资源拉取引擎设计（代号：司南 / 备选：灵犀）— 2026-08-01

> 针对性解决三个界面的"慢"困局，统一图标缓存与列表拉取，
> 并通过源适配器接口为 CurseForge 接入与整合包下载浏览铺路。

## 一、实测数据（慢的根因，2026-08-01 实测）

| 环节 | 延迟 | 说明 |
|---|---|---|
| mcimirror 搜索 API | **1897ms** | 列表慢的元凶；官方 api.modrinth.com 国内直连超时（16215ms 握手超时），只能走镜像 |
| 单张图标（镜像） | **4344ms**（波动 1.9s~8.7s） | 35KB 的 256x256 PNG 要 4.5 秒——镜像带宽/性能极差 |
| 20 并发图标 | **19s**（平均单个 9.8s） | **并发越多越慢**——现有 cacheBatchAsync 无并发控制，一页 20+ 瞬间全发打爆镜像 |
| 镜像缩略图参数 | 不支持（返回同尺寸） | 服务端无缩放能力 → 缩略图必须本地生成 |

### 隐藏 Bug：图标双重下载
`IconCache::resolveUrl()` 未命中缓存时返回**原始网络 URL** → QML `Image` 拿到网络 URL **再发起一次下载**。
同一张图 = IconCache 下载 1 次 + QML Image 下载 1 次 = **双倍流量 + 双倍镜像压力**。

### 其他现状缺陷
- 图标失败**无重试**，一次失败该图永久空白（直到重新搜索）
- 搜索**无结果缓存**：翻页/切 tab 回来重复打镜像（每次 ~2s）
- 图标无内存缓存：列表滚动反复解码（QML Image cache 只缓存解码结果于本地文件路径）
- 三个 IconCache 实例各用独立 QNAM，无 HTTP/1.1 连接池配置（HttpClient 已有 pooling，IconCache 没有）
- 无翻页预取：滚到底才发下一页请求

## 二、引擎架构

```
ResourceFetchEngine（司南）— QObject，backend 暴露，全局单例
├── ApiQueue        API 请求调度：全局并发 2、结果 LRU 缓存(TTL 300s)、失败重试 1 次
│                    源适配器（SearchAdapter）→ 现在 Modrinth/mcimirror；未来 CF / 整合包
├── IconPipeline    图标管线：并发 3、URL 去重合并、失败重试 2 次(退避)、
│                    下载→生成 88px 缩略图→双缓存（原图 + 缩略图）→ emit iconReady(url, localPath)
├── MemCache        内存图像缓存（QPixmapCache）：滚动零解码
└── DiskCache        磁盘：{data}/cache/res/{icons,thumbs,json}/，SHA1(url) 命名，LRU 淘汰
```

## 三、关键设计决策（针对实测根因）

1. **消除双重下载（核心修复）**：`resolveIconUrl` 未命中缓存时返回**空**（不再返回网络 URL）；
   QML 显示占位图，下载完成后 `iconReady(url, localPath)` 信号驱动 QML 更新 model 中对应项 → 每张图全链路只下载一次
2. **严格并发控制**：API 2 路 + 图标 3 路（实测 20 并发反而 2 倍慢）；HTTP/1.1 keep-alive 连接池
3. **缩略图本地生成**：下载原图 → QPixmap scaled 88px → 存 thumbs/；列表用缩略图（解码快、内存小），详情页用原图
4. **三层缓存命中**：内存 QPixmapCache → 磁盘缩略图 → 磁盘原图 → 才发起网络；二次浏览秒开
5. **搜索结果缓存**：同 URL 请求 300s 内直接返回缓存（翻页/切 tab 秒开，绕开镜像 2s 延迟）
6. **失败重试**：图标 2 次指数退避；搜索 1 次；全部失败走占位图
7. **预取**：当前页渲染后预取下一页搜索 + 下一页图标（可选，二期）
8. **源适配器接口**：`SearchAdapter`（抽象：search() + parse()），ModrinthAdapter 先行，
   CfAdapter（CurseForge API + 加密 key + 限流 60/min）与 ModpackAdapter（project_type:modpack）后续直接插装

## 四、对现有代码的改动

### C++（src/core/resource_fetch_engine.h/.cpp 新建；resource_backend 接入）
- `searchModsEx / searchShadersEx / 资源包搜索` → 改走 `engine->getJson(url, cacheable, cb)`（带缓存 + 并发 + 重试）
- `resolveIconUrl / resolveShaderIconUrl / resolveRpIconUrl` → `engine->iconLocalPath(url)`（空 = 未缓存）
- `cacheIconBatchAsync` 等 → `engine->prefetchIcons(urls)`（并发 3 排队下载）
- 新信号 `iconReady(url, localPath)` 由 backend 透传给 QML

### QML（DownloadPage.qml + 三个详情页）
- 新增 `Connections { onIconReady }`：遍历 model，把 icon==url 的项更新为 localPath（QML 端 model 值变更 → Image source 更新，自动重载）
- `Image` 已带 `asynchronous + cache + sourceSize`，无需大改；仅 icon 来源变为"本地路径或空"

## 五、验证标准
1. 首次搜索：列表文字 ~2s（镜像 API 延迟不可避免），图片渐进出现（3 路并发，每张 3-5s）
2. 翻页/切 tab 回来：**秒开**（搜索缓存 + 磁盘缩略图）
3. 滚动无闪烁、无空白（缓存命中即显；失败显占位）
4. 日志可见 `[引擎·司南]` 身份卡与并发/缓存统计
5. 后续 CF 接入：实现 CfAdapter 即可，UI 零改动
