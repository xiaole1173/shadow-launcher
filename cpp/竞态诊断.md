# 多MC+同加载器安装阶段竞态诊断报告

## 诊断时间
2026-07-29 08:47 北京时间

## 代码版本
`D:\latest-code\cpp\` — ShadowLauncher

## 结论

**是的，竞态确实存在。** 多 MC + 同一（或不同）加载器同步下载时，加载器安装阶段存在多个竞态问题，可能导致安装丢失、信号路由错乱、信号缺失、文件损坏等故障。

---

## 竞态问题列表

### 🚨 [P0] 1. 单个 `ModLoaderInstaller` 实例是所有加载器安装的共同瓶颈

**文件:** `version_backend.h:246` / `version_backend.cpp:184`

**描述:**
`VersionBackend` 只有一个 `ModLoaderInstaller* m_mlInstaller` 实例，所有加载器安装（Forge/NeoForge/Fabric/OptiFine）都通过这个实例串行化。

**实际流程:**
```
Task A (1.20.1-Fabric): MC 完成 → onVersionDownloadFinished
  → 检测到 hasPendingLoader && pendingLoaderMc=="1.20.1"
  → m_mlInstaller->installFabric("1.20.1", ...) → m_running = true
  → 开始下载 Fabric profile + libraries
  
Task B (1.20.2-Fabric): MC 完成 → onVersionDownloadFinished
  → 检测到 hasPendingLoader && pendingLoaderMc=="1.20.2"
  → m_mlInstaller->isRunning() == true → **被忽略，等待下一次事件** 🤷
```

**影响:**
- 第二个加载器安装被**直接跳过**（`if (m_running) return;` — 第230行）
- 即使后续再次尝试，也需要又有一次合适的信号触发，可能永远无法触发
- Task B 的加载器**永远不会安装**

### 🚨 [P0] 2. `m_modLoaderInstallId` 全局令牌竞态

**文件:** `version_backend.cpp:5631`

**描述:**
`VersionBackend` 用 `m_modLoaderInstallId = installName` 记录"当前安装的加载器属于哪个会话"。ModLoaderInstaller 的 `finished` / `progressChanged` / `stepProgress` 等信号处理函数都通过读取 `m_modLoaderInstallId` 来查找对应的 `DownloadSession`。

**竞态序列:**
```
T1: Task A 开始安装 Fabric(1.20.1)
    → m_modLoaderInstallId = "1.20.1-Fabric"
    
T2: Task A 的 ModLoaderInstaller::finished 信号触发
    → 处理函数读取 m_modLoaderInstallId → "1.20.1-Fabric" ✓ 正确

T1: Task B 开始安装 Forge(1.20.2)  
    → m_modLoaderInstallId = "1.20.2-Forge"  ← **覆盖了 A 的 ID**
    
T2: Task A 的 ModLoaderInstaller::finished 信号处理函数运行
    → 读取 m_modLoaderInstallId → "1.20.2-Forge" ← **错误！**
    → 把 Task A 的安装结果应用到 Task B 的 session 上
```

**影响:**
- 信号处理函数会更新错误的 `DownloadSession` 的进度/状态
- 一个任务成功，另一个任务显示失败或进度卡住

### 🚨 [P0] 3. ModLoaderInstaller 成员变量被并发覆盖

**文件:** `mod_loader_installer.cpp:230-258`

**描述:**
在 `m_running` 检查之前，各个 install 方法的开头就覆盖了成员变量：
```cpp
void ModLoaderInstaller::installForge(...) {
    qCInfo(...) << m_running;  // ❌ 未防护的读取
    if (m_running) return;     // 检查，但没有原子屏障
    m_running = true; m_cancelled = false;
    m_mcVersion = mcVersion;   // ❌ 被覆盖
    m_installName = installName; // ❌ 被覆盖
    ...
}
```

同时 `cancel()` 直接设置 `m_cancelled = true`（第51行），没有原子操作保护。如果两个任务几乎同时触发，可能在设置 `m_running=true` 之前就有另一个任务覆盖了参数。

### 🚨 [P1] 4. 静态 temp 文件提取的 TOCTOU 竞态

**文件:** `mod_loader_installer.cpp:2008-2050`

**描述:**
`extractBootstrapperPath()` 和 `extractJavaWrapperPath()` 写入固定的 temp 路径：
```cpp
QString dst = QDir::tempPath() + "/forge-installer.jar";
if (QFile::exists(dst)) return dst;  // TOCTOU: 检查→写入不是原子的
```

**竞态序列:**
```
T1: 检查 → 不存在 → 开始写入...
T2: 检查 → 不存在 → 开始写入... (覆盖 T1 正在写的文件)
```

结果: T2 读到的是 T1 正在写入的**部分文件**，T2 的写入也可能破坏 T1 稍后使用的文件。

### 🚨 [P1] 5. `downloadAndExtractJava` 共享缓存目录

**文件:** `mod_loader_installer.cpp:2128`

**描述:**
下载 Java 到 `java_cache/{minVersion}/` 固定目录。两个任务同时需要 Java 17 时：
```
T1: 创建 java_cache/17/bin/java.exe
T2: 创建 java_cache/17/bin/java.exe (覆盖正在进行中的文件)
```

### 🔴 [P2] 6. Bootstrapper 进程的 `runBootstrapperSync` 是线程安全但结果回调是主线程单通道

**文件:** `mod_loader_installer.cpp:2919`

`runBootstrapperSync` 本身在后台线程运行（`QtConcurrent::run`），通过 `QFutureWatcher` 在 `onBootstrapperFinished()` 回调到主线程。在同一时刻只能有一个 watcher 在活动——如果第二个启动，会覆盖 `m_bootstrapperWatcher` 指针并断开前一个的连接。

### 🔴 [P2] 7. Fabric 并行下载中的 `m_fabricLibIndex` 不是线程安全的

**文件:** `mod_loader_installer.cpp` (fabricStep2 相关)

`m_fabricLibIndex` 在没有锁的情况下被递增，如果 Fabric 下载回调交叉执行可能出问题。

## 各下载器实例化情况

| 组件 | 数量 | 是否独立 |
|------|------|----------|
| `VersionDownloader` (MC下载) | 每个任务一个 (`m_downloaders[versionId]`) | ✅ 独立实例 |
| `AssetDownloader` (资源文件) | 每个 VersionDownloader 内一个 | ✅ 独立 |
| `FileDownloader` (库文件) | 每个 VersionDownloader 内一个 | ✅ 独立 |
| `DownloadSession` (状态追踪) | 每个任务一个 (`m_downloadSessions[installId]`) | ✅ 独立 |
| `ModLoaderInstaller` (加载器安装) | **全局唯一** (`m_mlInstaller`) | ❌ **共享** |
| `VersionDownloader` 的下载 | 通过 `MAX_CONCURRENT=5` 限制并行数 | ⚠️ 有队列 |

结论：MC 下载阶段是真正的独立并行（每个任务有自己的 VersionDownloader/FileDownloader/AssetDownloader），不共享状态，因此没问题。
但**加载器安装阶段全部挤到唯一一个 ModLoaderInstaller 上**，所有竞态问题都在这里。

## 建议修复方案

### 方案 A（推荐）：每个安装任务拥有自己的 ModLoaderInstaller

**思路:** 不为每个任务创建一个独立的 `ModLoaderInstaller`，而是让 ModLoaderInstaller 变成无状态（stateless），只通过参数传递上下文。

**改动量:** 中
- 移除 `ModLoaderInstaller` 的所有成员变量（`m_mcVersion`、`m_installName` 等）——改为调用时传参
- 移除 `m_running` 状态检查——允许重入
- 信号改用 session ID 区分
- 静态方法改为线程安全（路径加唯一后缀或用 RAII 临时文件）
- `extractBootstrapperPath()` 返回带唯一后缀的临时文件路径
- `downloadAndExtractJava()` 用文件锁 + 完整下载验证
- 信号路由改为 per-call 回调（不是通过 `m_modLoaderInstallId` 查找）

### 方案 B（最小改动）：序列化加载器安装 + 修复信号路由

**改动量:** 小-中
- 在 `VersionBackend` 建一个加载器安装队列（`QQueue<QString> installQueue`），确保每次只做一次加载器安装
- 修复 `m_modLoaderInstallId` 的信号路由——在信号 lambda 中 capture installId，不依赖全局变量
- 修复 `extractBootstrapperPath`/`extractJavaWrapperPath` 的 TOCTOU
- 修复 `downloadAndExtractJava` 的并发

### 方案 C（针对问题修复）：只修复关键点

**改动量:** 小
1. 修复信号路由：将 `m_modLoaderInstallId` 替换为信号 lambda 中 capture 的 `installId`
2. 加载器安装失败时（因为 `m_running=true`）加入重试队列，而不是静默丢弃
3. 修复静态方法 TOCTOU（加文件锁或唯一后缀）
4. 修复 `downloadAndExtractJava` 的并发
