## 一、现存故障核实（代码审计逐条对照）

### 1.1 FileDownloader 迭代劣化（6129062→HEAD 六个提交叠加）

6129062 之后共 6 个提交改动 5 个文件（file_downloader.cpp/.h、modpack_downloader.cpp/.h、modpack_install_task.cpp），核心机制：

| 提交 | 引入机制 |
|---|---|
| b05f8b4 | 队列级兜底重试雏形 |
| 088f7e4 | state=2 修复放开为通用（唯一流入 MC 的行为改动） |
| c0076c4 | fileProgress 与 progressChanged 同节奏节流（250ms） |
| 107c8cd | 速度源改全局 EMA（currentSpeedMBps）；重试轮线程配额隔离 |
| ec870e4 | attemptLimit=1/源（删源级整表重试）；队列级多轮重试 kMaxRetryRounds=5，每轮新引擎 |
| e6bf95a | 文件级 30s 重试预算 modBudgetStartMs；15s 空闲超时；30s transferTimeout 兜底；cleanup 线程配额守卫 |

**耦合冲突点（已核实）**：
1. **预算 + attemptLimit=1**：任何瞬时抖动（镜像 502 风暴、首字节慢）直接判文件失败；预算耗尽时 cleanup 跳过失败分片重下 → 大文件单分片失败即整文件失败 → 下一轮整文件重下（浪费且放大失败率）。
2. **15s 空闲超时对慢速镜像激进**：镜像高峰期内"慢但活着"的连接被掐；30s transferTimeout 兜底会误杀慢速大文件（readyRead 重置只保护 QTimer 空闲超时，不保护整体 transferTimeout）。
3. **线程配额守卫（cleanup）**：`m_activeThreads >= m_maxThreads` 时失败分片保留 state=4 不重下 → 与"所有线程卡在慢请求"叠加 → 剩余文件数不变、进度停滞（用户实测的末期停滞根因之一）。
4. **每轮新引擎**：重试轮重建 FileDownloader → DNS 重解析、连接全重建，无任何复用；且重试轮 6 线程与正常轮 12 线程参数不同，进度基数（m_round1Done）跨轮累计逻辑复杂（countFinishedFailed/queueProgress 多处修正）。

### 1.2 网速虚高 / 不归零（根因：四套算法并存）

当前存在 **4 套互不一致的速度计算**：

| # | 位置 | 算法 | 口径 | 去向 |
|---|---|---|---|---|
| 1 | FileDownloader::speedTick → m_emaMbps | 100ms 差分 + 30 条加权 + 0.5/0.5 EMA | 全局已下载字节（**含 cache**） | 引擎日志 "[速度] EMA=..."、currentSpeedMBps() |
| 2 | VersionBackend::updateDownloadProgress → st.smoothSpeed | α=0.15 EMA | 网络字节（**排除 cache**） | MC 卡片 |
| 3 | DownloadSession::recordBytes → m_speed | 差分 + 30 条加权 + 0.4/0.6 EMA | 原始字节（**含 cache**） | 会话层/合并卡片 |
| 4 | QML DownloadQueueCard._dispSpeed | 后端值 ×0.3 趋近；后端==0 时 ×0.5 衰减 | 二次平滑 | 界面显示 |

**不归零根因**：算法 2/3 都是"30s 无数据才跳 0"（`deltaBytes==0 && deltaMs>30000 → 0`），期间保持旧值 → QML 的 ×0.5 衰减分支**永远不触发**（它只在后端值==0 时生效）→ 界面速度停流后悬浮不落。
**不一致根因**：算法 1/2/3 的 EMA 系数、窗口、cache 计入口径全部不同；模组+MC 并行期卡片显示两者之和（算法 1+2），与任一引擎日志都不可比。

### 1.3 分片/HTTP2/超时/重试补丁耦合 + 架构短板（已核实）

- 单引擎双场景：`runWorker` 内用 `m_modpackMode` 开关交织 MC（64 线程 / per-host 4 / 50MB 分片阈值 / 每源 6 次 / 60s-30s 超时）与模组（12 线程 / per-host 12 / 1MB 阈值 / 每源 1 次 / 15s 空闲）两套参数。任何一处"通用化"修复（如 088f7e4）都会同时改变另一条路径的行为。
- **无连接复用**：每个 DownloadWorker 内 `QNetworkAccessManager mgr` 局部实例 → 海量小文件每文件新建 TCP 连接；代码里的 `QHttp1Configuration(255/host)` 在单 QNAM 场景下无效。
- 引擎间：各自独立 QThreadPool（上限 128）不互抢线程，但合并安装时模组 12 路 + MC 64 路共 76 个并发连接同时打镜像，网络层互相冲击。

### 1.4 MC 本体下载"锁死 1MB/s"根因（审计更正：主要不是补丁污染）

**结论先行：MC 慢的根因在基线 6129062 就存在**，6129062 后的补丁绝大部分是 modpack-only，真正流入 MC 的只有 state=2 通用化（该修复方向正确）。机制链：

1. **基线分片对 MC 是死代码**（详见第二节豁免依据）：MC 模式 state=2 永不被设置 → Phase2 的 `prep>dl` 守卫恒真 → tryAddThread 永不执行 → client.jar 等 >50MB 文件永远单线程。
2. **速度门限**（基线即有，HEAD 未改）：`if (!m_modpackMode && curMbps*1024*1024 >= floor) return;` —— 单连接速度 ≥ 下限（峰值 85%）时永不追加线程，分片只可能在慢启动窗口内发生。
3. **per-host 上限 4**（kMaxPerHost，hostCanAccept）：BMCLAPI/官方 CDN 每 host 最多 4 个并发请求。
4. BMCLAPI 单连接限速 → 1-2 个大文件单连接 → 实测 ~1MB/s 量级。

**推论**：仅回滚不会恢复 MC 满速；必须靠"豁免保留分片修复 + MC 门限/并发参数调整"组合（见 2.3、2.4）。

### 1.5 源偏好配置失效（证据确凿）

- **主犯**：`mod_loader_installer.cpp:1423-1436` `mirrorMavenUrl()` 硬编码把所有 maven 域替换为 BMCLAPI：
  `maven.minecraftforge.net` / `files.minecraftforge.net` / `maven.neoforged.net` / `libraries.minecraft.net` / `repo1.maven.org/maven2` → `bmclapi2.bangbang93.com/...`，**完全不读 fileDownloadSource 设置**。Forge 版本列表（:1363）、OptiFine（:312）同样硬编码 BMCLAPI。
- **对照**：version_downloader.cpp:271-294/315 已正确读取 `fileSource`（PreferOfficial/AutoSwitch 时官方 URL 排前）→ MC 本体/库走 VersionDownloader 的路径没问题，问题集中在**加载器安装器（Forge/NeoForge/OptiFine）的库下载路径**。
- 设置定义：settings_backend.h:229 `0=PreferMirror, 1=PreferOfficial(默认), 2=AutoSwitch`；QML 三项下拉框（SettingsGeneralPage.qml:763-796）。

### 2.2 豁免校验：基线 6129062 分片逻辑缺陷（依据）

**缺陷成立，允许保留 MC 分片加速代码。** 证据（基线 file_downloader.cpp）：

1. **基线 :552**：`if (th->state == 1 && m_modpackMode) th->state = 2;` —— state=2（downloading）**仅在模组模式设置**，MC 模式任何路径都不会把线程状态推进到 2。
2. **基线 :304-310**：Phase2 分片守卫 `prep>dl → continue`，其中 `state<2 计为 prep`、`state==2 计为 dl`。MC 模式所有线程恒为 state<2（prep），dl 恒为 0 → **tryAddThread 永不执行**。
3. **基线 :140-141**：`isNoSplit = fileSize < (m_modpackMode ? 1MB : 50MB)` —— MC 声明的 50MB 分片阈值**永远不生效**，与分片配套的 tryAddThread / splitPoint(40% 切割) / mergeFile 对 MC 是死代码。

结论：设计上 MC >50MB 文件应多线程分片，实际因 state 机缺陷从未分片——功能缺陷明确。豁免成立。

### 2.3 豁免保留形态与作用域隔离

- **保留一行**：`if (th->state == 1) th->state = 2;`（088f7e4 的核心改动）。
  - 对模组路径行为与基线**完全一致**（基线模组模式本就设置 state=2），仅改变 MC 路径 → 天然满足"仅作用于 MC 资源下载、不侵入模组链路"的隔离要求。
  - 如需显式表达隔离，可写成 `if (th->state == 1 && (m_modpackMode || !m_modpackMode))` —— 无意义，直接保留无条件写法并加注释即可。
- **连带调整（恢复 MC 满速的必要项，非强制但强烈建议）**：
  - 速度门限（基线 :288 / HEAD 同）：`if (!m_modpackMode && curMbps*1024*1024 >= floor) return;` → 建议 MC 与模组一致"无视速度下限直接分片"（仅当 `active >= maxThreads` 或 `prep>dl` 才停），或把门限降级为纯防抖。注意：PCL 也有同款门限（`Speed >= NetTaskSpeedLimitLow 则不加线程`，NetTaskSpeedLimitLow 初始 256KB、动态=近 10 条均速×0.85），PCL 靠慢启动窗口（连接建立期速度≈0 < 下限）完成分片；我们的门限逻辑同构，**回滚后实测分片是否在慢启动窗口内触发，若未触发再放宽**。
  - per-host 上限：MC 的 kMaxPerHost=4 与 PCL 不同（PCL 无 per-host 连接数上限，64 线程全局共享；仅 bmclapi/github/optifine 等域名白名单禁分片 + BMCLAPI 每启一线程 Sleep(100) 限频）。建议 MC 场景放开到 8-16 或引入"域名白名单单线程"语义；**BMCLAPI 保持单线程/低并发**，官方 CDN（piston-data.mojang.com）走多线程分片——这是 PCL 提速的关键设计。

## 三、网速统计模块全盘重构方案

目标：**C++ 底层唯一速度源 = 引擎日志同源的全局 EMA/滑动窗口值；QML 禁止二次计算；模组+MC 并行聚合；停流平稳归零；界面与日志完全一致。**

1. **唯一数据源**：FileDownloader 速度统计（speedTick → m_emaMbps）作为唯一速度源。改造口径：速度采样用**网络字节**（`m_downloadedBytes - cacheBytes`，与 VersionBackend 现有口径对齐），避免 cache 命中文件造成瞬时虚高。日志 "[速度] ..." 与推送同源同值。
2. **算法对齐 PCL（推荐）**：
   - 100ms 差分采样 → 30 条滑动窗口**线性加权**（最新权重=N，最旧=1）→ 显示值 = 加权平均；
   - 停流归零：窗口内连续 0 采样，加权平均约 3s 内**自然滑落至 0**（PCL 语义，天然"平稳下降"）；
   - 替代方案（保留 EMA）：把 0.5/0.5@100ms 改为时间常数 ~2s 的指数衰减（当前 1s 内跳零太陡，观感像悬崖）。
   - **删除 30s 跳零逻辑**（VersionBackend::updateDownloadProgress 与 DownloadSession::recordBytes 中 `>30000 → 0` 两处）。
3. **消除重复计算**：
   - DownloadSession::recordBytes 删除速度段（只保留进度）；其速度改从引擎 EMA 转发。
   - VersionBackend::updateDownloadProgress 的 α=0.15 第三套 EMA 删除，st.speed 直接取 VersionDownloader 引擎 EMA。
4. **聚合与一致性**：卡片速度 = 模组引擎 EMA + MC 引擎 EMA；引擎日志同步打印 `[速度] 模组=X MB/s MC=Y MB/s 合计=Z MB/s`（1s 节流）→ 界面数值与日志**逐条可比**。
5. **QML 收口**：DownloadQueueCard 删除 `_dispSpeed` 二次平滑（`nd.speed>0 → 趋近 ×0.3`、`否则 ×0.5` 两分支），直接显示后端推送值（fmtSpeed 格式化保留）；后端停流时持续推送衰减值直至 0（由第 2 条自然归零保证）。

## 四、主流启动器 源码调研结论（对应调研 4 目标）

> 关键更正：PCL 仓库中**不存在** DownloadTask/DownloadManager/SpeedTest 等类。真正引擎在 `Modules\Base\ModNet.vb`：单文件=`NetFile`(L652)+`NetSource`(L429)+`NetThread`(L501)；批量=`LoaderDownload`(L1387)；全局调度=`NetManagerClass`(L1715)；任务框架=`LoaderTask(Of TIn,TOut)`(ModLoader.vb:263)。整合包安装逻辑在 `Modules\Minecraft\ModModpack.vb`（ModDownloadLib.vb 实为"合并安装"库）。版本列表 JSON 不走下载引擎，走 `NetRequestByClientRetry`（ModNet.vb:44）。

### 4.1 分层设计（目标 1）

**游戏本体 / 依赖库 / 模组完全共用同一套引擎**（NetFile + LoaderDownload + NetManagerClass），差异只在：
- **URL 数组顺序**：`DlSourceOrder = If(DlSourcePreferMojang, 官方.Union(镜像), 镜像.Union(官方))`（ModDownload.vb:1223-1225）；DlSourcePreferMojang = 源设置=2，或 =1 且测速偏好 Mojang（:1215-1219）。每个 URL 变成一个 NetSource，失败源标记 IsFailed 后 GetSource 自动跳过（ModNet.vb:680-700）。
- **FileChecker**（哈希/大小/IsJson）与 **SimulateBrowserHeaders**（模组下载伪装浏览器）。
- 例：客户端 jar=NetFile(多源, sha1+MinSize)（ModDownload.vb:9-24）；assets/libraries 大批量=LoaderTask 分析 + LoaderDownload 下载（:48-102），URL 经 DlSourceAssetsGet/DlSourceLibraryGet（:1245/:1258）生成官方+BMCLAPI 列表；模组经 DlSourceModGet 换 MCIM 镜像（:1301）→ ResourceVersion.ToNetFile（ResourceVersion.vb:381-388）。
- 加载器 installer 主文件**硬编码镜像优先**：Forge/NeoForge BMCLAPI maven → 官方 maven（ModDownloadLib.vb:1080-1091）；OptiFine BMCLAPI → 官方（:481-503）——与我们的 mod_loader_installer 同构。

### 4.2 模组批量下载专属（目标 2）

- **并发管控**：全局线程上限 `NetTaskThreadLimit = Settings("ToolDownloadThread")+1`，默认 63+1=**64 线程全局共享**（ModNet.vb:384-388；Settings.vb:117）；两个常驻调度线程 ThreadStarter 0/1 每 20ms 轮询（:1802-1803、:1847-1848），按 `File.Uuid Mod 2` 分片负载（:1809）；先为 WaitingToDownload 文件开首线程（:1817-1821），全局速度 ≥ 下限才为进行中文件追加线程（:1823-1841）；追加条件还有"prep 线程数不能多于 dl 线程数"（:1838，与我们 managerTick 同款守卫）。
- **多源切换时机**：无独立重试函数——换源由 NetFile 引擎统一完成：失败 → 遍历 Sources 跳过 IsFailed；**文件级兜底**：全部源失败且未重试过 → 所有源标记"单线程不可断点续传"（SourcesOnce）逐个顺序重试一遍（Retried 标记仅一次，:1181-1196）；源禁用判定（SourceFail :1146-1220）：合并失败、Range 不支持(416)、502、404、DNS 失败、无返回数据、磁盘不足、(403/429 且非 bmclapi)、连续失败计数超 `NetTaskThreadLimit.Clamp(5,30)` 且已下载<1B、或 FailCount > 线程上限+2。
- **重试机制**：**PCL 是严格语义——单文件失败 = 整个整合包任务失败中止**（NetFile.Fail → LoaderDownload.OnFail → 取消全部，ModNet.vb:1327-1338、1657-1696；ModLoader.vb:576-578）。容错只在"连续失败计数"：`FailCount > Min(10000, Max(FileRemain*5.5, ThreadLimit*5.5+3))` 才整体失败（:1426-1428），即剩余文件越多越宽容。**这与我们"队列级多轮重试"设计相反**——建议新引擎保留有限轮重试（抗镜像风暴体验更好），但单轮内参数对齐 PCL（快速失败、逐源、SourcesOnce 式兜底）。
- **小文件队列调度**：全局单队列（ConcurrentDictionary 按本地路径，**跨任务同路径文件复用**，ModNet.vb:1896-1911）；无手动分批、无优先级，靠线程上限自然限流；下载前先做"已存在文件查找"——FileChecker 带 hash/size 时扫描各版本文件夹按哈希匹配，命中直接复制本地而非下载（:1513-1580，最多 8 线程检查，:1531-1544）。
- **分片触发阈值**：`IsNoSplit = IsUnknownSize OrElse FileSize < 1MB`（:747-750）→ **1MB 以下不分片、单线程内存流下载**；分片最小单元 `FilePieceLimit = 256KB`（:845，最大未下载片段 <256KB 不再加线程，:930-934）；新片从最大片末端倒推 40% 处切入（:935）；片数不预设，动态增长直到线程上限或碎片 <256KB。

### 4.3 网速统计 / 平滑 / 空闲归零（目标 3）

**PCL 没有 EMA**，是"差分测速 + 滑动窗口线性加权"，归零由窗口自然实现：
- 线程/文件级：200ms 节流惰性差分（`(DownloadDone-SpeedLastDone)/(DeltaTime/1000)`，ModNet.vb:587-606、773-789）；无数据不衰减（旧值保持），归零发生在管理器层。
- **全局显示**（NetManager.Speed，管理线程每 100ms 刷新，:1852-1866）：差分采样 → `SpeedLast` 列表插头部、**最多 30 条（≈3s 窗口）**（:1752-1779）→ 线性加权（最新权重=N，最旧=1）→ 显示值；**无数据时窗口内连续 0，加权平均 ~3s 自然滑落归零**。
- 动态下限：窗口 ≥10 条时 `Limit = 近 10 条均速 × 0.85`，高于现值则提升 `NetTaskSpeedLimitLow`（初始 256KB/s，:1773-1779）→ 只用于"速度够就不加线程"。
- 限速：令牌桶（管理线程 100ms 注入 High/10 字节，下载线程写前自旋等令牌，:1070-1074、:1855）；默认不限速（ToolDownloadSpeed 默认 42=-1）。

### 4.4 海量小文件网络参数 / 连接复用 / 超时（目标 4）

- **连接复用（与我们差距最大的点）**：下载用**进程级单例 HttpClient（ThreadClient）全局共享**，天然复用连接池（ModNet.vb:414-418）；API 请求另有 CacheCow 缓存客户端（:225-232，HTTP 缓存落盘 PathTemp\Cache\Http）。
- 全局网络调优（Application.xaml.vb:103-107）：`ServicePointManager.Expect100Continue=False / UseNagleAlgorithm=False / EnableDnsRoundRobin=True / ReusePort=True / DefaultConnectionLimit=10000`（=不限制，无 per-host 上限）。
- **超时**：下载线程单次读写动态 `Min(Max(ConnectAverage,15000)*(1+FailCount),30000)` ms（:982）；无数据超时 = 距上次收到数据 > 线程 Timeout（:1093-1097）；**龟速断开**：包间隔 >5s 且速度 <1K/s 强制断开（:1099-1101）；API 重试 10s→30s→4s（403/404 不重试，429 睡 10s，:53-73）。
- **自定义 DNS/IP 优选**：请求前手动解析换最高可靠性 IP（保留 Host 头），`IPReliability = v*0.5 + result*0.5`（:311-364），失败 IP 降 -0.01 促使换 IP；排除严格 SNI 域（mojang.com/minecraft.net/minecraftservices.com）；DNS 失败 1 分钟冷却；IPv4/IPv6 择优（Modrinth IPv4 加权 -0.1）。**我们 FileDownloader 已有同款 resolveHost 雏形**（dnsCache/kDnsCacheMs/kDnsFailureBackoffMs），方向一致。
- **镜像友好**：BMCLAPI 每启一线程 Sleep(100) 限频（:1820、:1840），403/429 不禁用 bmclapi 源（:1159）；bmclapi/github/optifine 等域名白名单**禁分片单线程**（:926-927）。
- 缓冲 16KB/次、线程优先级 BelowNormal（:945）；Accept-Encoding 走 AutomaticDecompression 自动协商（我们模组路径的 `Accept-Encoding: identity` 是为 SHA1 一致性，**保留合理**）。

## 五、独立模组专属下载引擎隔离开发思路

### 5.1 物理隔离

- 新类 `ModDownloadEngine`（建议 `cpp/src/core/modpack/mod_download_engine.h/.cpp` 独立文件），**完全不复用 FileDownloader**；FileDownloader 回归纯 MC 本体/加载器/库场景（基线 + 豁免项）。
- 引擎级**共享 QNetworkAccessManager 单例**（PCL ThreadClient 式连接池复用）+ 独立 QThreadPool 实例 + 独立速度统计器（第三节 SpeedMeter）。
- 与 MC 引擎互不共享线程池、连接、统计——合并安装时两套资源完全隔离。

### 5.2 针对模组海量小文件的参数（对齐 PCL 结论）

| 项 | 方案 |
|---|---|
| 并发 | 默认 12-16 线程；**per-host 限频替代硬上限**：MCIM 镜像每启一线程 Sleep(100)（PCL 同款），防镜像限流饿死连接 |
| 重试 | 每源 1-2 次快速失败 → 镜像降级官方 → 文件级"全部源单线程逐个兜底一遍"（SourcesOnce 式）→ 队列有限轮重试（建议 ≤3 轮，保留抗镜像风暴能力，不做 PCL 的"单文件失败=全任务失败"） |
| 超时 | 动态 `Min(Max(ConnectAvg,15s)*(1+FailCount),30s)` + 无数据超时 + 龟速断开（>5s 且 <1K/s），删除固定 15s 空闲与 30s 预算制 |
| 分片 | 保持 <1MB 不分片；>1MB 可选分片但默认关（模组场景罕见大文件） |
| 校验 | SHA1/大小校验保留；Accept-Encoding: identity 保留 |
| 源排序 | URL 构造前读取 `fileDownloadSource`：PreferMirror→MCIM 优先+官方兜底；PreferOfficial→官方 API/CDN 优先+MCIM 兜底；AutoSwitch→超时自动降级 |

### 5.3 接口兼容（上层零改动）

ModpackDownloader 内部仅把 `m_fd`（FileDownloader 实例）替换为 ModDownloadEngine 实例，对外契约不变：
- 信号：`progressChanged(int,int,qint64,qint64)` / `fileProgress(url,name,rx,total,path)` / `fileFinished(path,bool,error)` / `logMessage(QString)` / `allFinished(bool)` / `queueProgress(...)`；
- 方法：`addFile(...)` / `start()` / `cancel()` / `completedFiles()` / `failedFiles()` / `currentSpeedMBps()`；
- 因此 **DownloadQueueCard、任务取消、文件回滚、导入 Overlay、步骤展示全部无需修改**，仅底层驱动替换。

### 5.4 保留原有稳定能力

- MCIM 镜像优先 + 官方源降级（并入源偏好设置排序）；
- 文件哈希校验（SHA1）；
- 任务终止全量文件回滚（ModpackInstallTask 既有清理逻辑不动）。

### 5.5 附带修复（源配置生效）

- `mod_loader_installer.cpp::mirrorMavenUrl()` 参数化：传入 `DownloadSourcePolicy`，PreferOfficial 时改为**官方 maven 优先**替换（libraries.minecraft.net / maven.minecraftforge.net / maven.neoforged.net / repo1.maven.org），BMCLAPI 作兜底；AutoSwitch 维持 BMCLAPI 优先 + 失败降级。
- Forge 版本列表（:1363）、OptiFine（:312）的 BMCLAPI 硬编码一并接入设置。
