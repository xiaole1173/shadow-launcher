修复超额下载根因：fileSize 被分片响应缩小 → isNoSplit 翻转 → 无 Range

用户实测：fastutil 200 响应 23.9MB 只留 132KB（超额 23.8MB），
26.2.jar 206 响应 39MB（超额 34MB）——浪费流量 + 卡顿。

根因（Qt/curl 实测排除服务器和 Qt 问题——官方 CDN 正确返回
206 + 精确分片）：
1. 首线程 split 后，旧请求（Range 全文件）继续返回全文件数据
   ——split 时机导致的固有开销（一次性的，可接受）
2. 【严重】首线程 split 后响应是分片（206，contentLen=分片大小如
   5MB）——789 行用 actualSize != fileSize 更新 fileSize → 39MB
   文件被改成 5MB → isNoSplit 翻转（<1MB 时）→ 后续请求无 Range
   → 服务器返回全文件 200 → 23.9MB 只留 132KB（fastutil 实测）

修复：fileSize 更新只允许补差（actualSize > fileSize），不允许缩小
——分片响应（contentLen=分片大小）不会再把文件大小改小；isNoSplit
保持正确 → 请求始终带 Range → 不再全文件超额下载。

Qt/curl 实测证据：piston-data.mojang.com 带 Range: bytes=0-5032092
返回 206 + Content-Range 0-5032092/39193383 + 精确 5MB 数据。
